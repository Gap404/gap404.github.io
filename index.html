配置文件的结构

nginx由由配置文件中指定的指令控制的模块组成。指令分为简单指令和块指令。一个简单的指令由名称和参数组成，用空格分隔，并以分号（;）结尾。块指令的结构与简单指令相同，但它不是分号，而是以一组被大括号（{和}）包围的附加指令结束。如果块指令可以在大括号内包含其他指令，则称为上下文（示例：事件、http、服务器和位置）。

放置在任何上下文之外的配置文件中的指令都被视为在主上下文中。events和http指令位于main下文、http中的server和server中location中。

文件权限

SUID

  • owner x位为s的
  • SUID 权限仅对二进制可执行文件有效
  • 如果执行者对于该二进制可执行文件具有 x 的权限，执行者将具有该文件的所有者的权限
  • 本权限仅在执行该二进制可执行文件的过程中有效
    1.例如passwd程序

SGID

  • group s位为s的
  • 用户若对此目录具有 r 和 x 权限，该用户能够进入该目录
  • 用户在此目录下的有效用户组将变成该目录的用户组
  • 若用户在此目录下拥有 w 权限，则用户所创建的新文件的用户组与该目录的用户组相同

SBIT

  • SBIT 目前只对目录有效，用来阻止非文件的所有者删除文件。

你说得对。从 Linux 运维视角，网络排查的核心确实应该围绕 ping、curl、nc、ss/netstat 展开，而不是上来堆一大批配置命令。

我前面的回答偏向“系统网络配置排错”，没有突出运维中最重要的思路：

先定义故障现象，再用最小工具验证网络路径、端口、服务和连接状态。

这几类命令不是互相替代的，而是分别回答不同问题。

一、为什么是这四类命令

命令 主要回答的问题 所在层次
ping 主机或路径是否基本可达？延迟、丢包如何？ ICMP / IP 层
nc 某个 TCP/UDP 端口是否能建立连接？ TCP/UDP 传输层
curl HTTP、HTTPS、代理、TLS、应用响应是否正常？ 应用层
ss / netstat 本机监听了什么？连接处于什么状态？ 本机 Socket 状态

Linux 运维最关心的通常不是“网卡有没有地址”本身，而是：

  • 机器能不能到目标机器？
  • 目标端口能不能连？
  • 目标服务有没有监听？
  • TCP 连接卡在哪个状态？
  • 应用层是否返回正确响应？
  • 故障是在客户端、网络、服务端还是应用？

五、ss：判断本机服务和连接状态

ping、nc、curl 主要是从客户端观察远端。

ss 则是从本机观察：

  • 谁在监听端口
  • 哪些连接已经建立
  • 哪些连接正在等待
  • 是否有大量半连接
  • 哪个进程占用了端口

在 Arch Linux 上，优先使用 ss，而不是 netstat。netstat 属于较老的工具，很多系统默认不安装；ss 通常来自 iproute2，直接读取内核 Socket 信息，速度也更快。

CLOSE-WAIT

对端已经关闭连接，但本机应用没有及时关闭自己的文件描述符。

大量 CLOSE-WAIT 常常指向：

  • 应用程序没有正确释放连接
  • 代码连接泄漏
  • 后端连接池异常
